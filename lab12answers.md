# Лабораторная работа №12. Ответы на контрольные вопросы

## Вопрос 1. Порядок байт (Little-Endian vs Big-Endian)

### Зачем мы переворачивали байты

В структуре `sockaddr_in` для `connect()` нам нужно было записать два числа в **сетевом порядке байт**:

- **Порт 8080** в шестнадцатеричном виде — `0x1F90`. Мы записали в память `0x901F`.
- **IP-адрес 127.0.0.1** — `0x7F000001`. Мы записали `0x0100007F`.

Это **не случайность и не прихоть ассемблера** — это требование сетевых протоколов.

### Фундаментальная разница: x86-64 и Internet

**Процессоры x86-64 — Little-Endian (LE).** Младший байт числа лежит по **меньшему** адресу в памяти.

Например, число `0x12345678` в памяти x86-64 выглядит так:
```
адрес +0: 78
адрес +1: 56
адрес +2: 34
адрес +3: 12
```

**Сетевые протоколы (TCP/IP) — Big-Endian (BE).** Старший байт идёт первым — то есть по **меньшему** адресу лежит **старший** байт.

Число `0x12345678` в сетевом формате выглядит так:
```
байт 0: 12
байт 1: 34
байт 2: 56
байт 3: 78
```

Big-Endian для сетей выбрали **исторически**: в первых сетях (ARPANET) использовались процессоры Motorola 68000 и другие BE-архитектуры, и этот порядок стал стандартом в RFC-документах. Протокол IP не меняют с 1981 года, поэтому все современные LE-процессоры (x86, ARM) **обязаны** переводить числа в BE перед отправкой в сеть.

### Разбор порта 8080

Порт 8080 = `0x1F90`. В памяти x86-64 (LE) его надо хранить так:
```
байт 0: 0x90   ← младший байт сначала
байт 1: 0x1F   ← старший байт потом
```

А в структуре `sockaddr_in` поле порта имеет тип `uint16_t` — 2 байта. NASM позволяет записать это как `dw 0x901F` — **число, которое в памяти разложится именно так**.

### Разбор IP 127.0.0.1

IP 127.0.0.1 = `0x7F000001`. В памяти x86-64 (LE) его надо хранить так:
```
байт 0: 0x01   ← младший байт сначала
байт 1: 0x00
байт 2: 0x00
байт 3: 0x7F   ← старший байт потом
```

NASM-выражение `dd 0x0100007F` разложится в памяти ровно так.

### Что если бы мы не перевернули

Если бы мы записали `dw 0x1F90` и `dd 0x7F000001` «как есть», ядро Linux прочитало бы из структуры:

- **Порт:** `0x1F90` в LE = байты `90 1F` = число `0x901F` = **36919**. Подключение ушло бы на порт 36919, а не на 8080.
- **IP:** байты `01 00 00 7F` = число `0x7F000001` в BE = адрес **1.0.0.127**, а не `127.0.0.1`.

То есть данные улетели бы «не туда».

### Встроенные функции перевода

В языках высокого уровня есть готовые функции для этого:

- **Python:** `socket.htons(8080)` (host-to-network short) для порта; `socket.inet_aton("127.0.0.1")` для IP.
- **C:** `htons()`, `htonl()`, `inet_addr()`.
- **NASM:** приходится переворачивать вручную, потому что ассемблер работает **на уровне байт**, а не абстракций.

## Вопрос 2. Анализ регистров — как ядро возвращает ошибки

### Что было в регистре RAX после неудачного connect

В нашем эксперименте со `strace` без сервера:

```
connect(3, {sa_family=AF_INET, sin_port=htons(8080), ...}, 16) = -1 ECONNREFUSED (Connection refused)
```

**`connect()` вернул `-1`.** То есть в регистре `RAX` после `syscall` было записано **отрицательное число**: `-1` (в шестнадцатеричном виде — `0xFFFFFFFFFFFFFFFF`, потому что регистр 64-битный и хранит **дополнительный код** отрицательного числа).

### Соглашение ядра Linux о возврате ошибок

Linux x86-64 использует **систему кодов ошибок через отрицательные значения**. После любого `syscall` программа должна проверить регистр `RAX`:

- Если `RAX >= 0` — системный вызов **успешен**, `RAX` содержит полезный результат (например, число прочитанных байт, дескриптор сокета).
- Если `RAX < 0` — системный вызов **провалился**, и **модуль** числа — это код ошибки. То есть `RAX = -13` соответствует ошибке `EACCES` (13), `RAX = -111` — `ECONNREFUSED` (111), `RAX = -98` — `EADDRINUSE` (98).

**Конкретно для нашего случая:**
- `ECONNREFUSED` = **111** (в `/usr/include/asm-generic/errno.h`).
- После `syscall` в `RAX` находится `-111` = `0xFFFFFFFFFFFFFF91` в дополнительном коде.

### Как ядро записывает отрицательное значение в RAX

На уровне кода ядра Linux x86-64 это делается так: в конце обработки syscall'а ядро проверяет, была ли ошибка. Если была — оно **записывает `-errno`** в поле `RAX` регистровой части сохраняемого контекста. При выходе из ядра через `sysret` это значение попадает в регистр `RAX` пользовательского процесса.

### Как программа в Ring 3 узнаёт об ошибке

**На чистом ассемблере** программист **обязан сам** проверить `RAX`:

```nasm
    mov rax, 42         ; sys_connect
    ...
    syscall

    test rax, rax       ; проверяем знак RAX
    js .error           ; если отрицательное — переход на обработку ошибки
    ; ... успешный код ...
    jmp .done

.error:
    neg rax             ; получаем модуль: 111
    ; теперь RAX = 111 = ECONNREFUSED
    ; можно обработать или вывести
.done:
```

**На языках высокого уровня** эту проверку делает рантайм:

- **C:** функция-обёртка из `glibc` сама проверяет `RAX`, и если он отрицательный — устанавливает глобальную переменную `errno` и возвращает `-1`.
- **Python:** интерпретатор видит отрицательный `RAX`, забирает `errno` из модуля числа и **выбрасывает соответствующее исключение** — `ConnectionRefusedError` для `ECONNREFUSED`.

### Что произошло с `SIGPIPE`

**Дополнительно к ошибке `connect`** в нашем эксперименте ядро послало процессу **сигнал `SIGPIPE`**:

```
--- SIGPIPE {si_signo=SIGPIPE, si_code=SI_USER, si_pid=820, si_uid=1000} ---
+++ killed by SIGPIPE +++
```

**Почему:** после неудачного `connect` сокет находится в **невалидном состоянии**. Когда мы попытались сделать `write()` в него, ядро не только вернуло `EPIPE` в `RAX`, но и **само** послало сигнал `SIGPIPE` — «ты пишешь в мёртвый сокет, это недопустимо».

**Поведение по умолчанию для `SIGPIPE`:** **завершить процесс**. Что и произошло — `killed by SIGPIPE`. Поэтому строка `sys_exit` (60) в нашей программе **не выполнилась**.

**Чтобы этого избежать**, программы обычно:
- либо **игнорируют `SIGPIPE`** через `signal(SIGPIPE, SIG_IGN)`;
- либо используют флаг **`MSG_NOSIGNAL`** при `send()` (Linux-специфичный), который отключает генерацию сигнала.

Это **второй способ**, которым ядро общается с Ring 3: не через возвращаемое значение, а через **сигналы**. Первый — через `RAX` (отрицательные числа), второй — через асинхронные сигналы типа `SIGPIPE`, `SIGSEGV`, `SIGFPE`.

## Вопрос 3. Сравнение абстракций — путь от Python до регистров

Рассмотрим цепочку трансформации от вызова `socket.send("Hello")` в Python до конкретных машинных инструкций и syscall'ов ядра.

### Уровень 1. Python-код

```python
import socket
s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.connect(("127.0.0.1", 8080))
s.send(b"Hello")
```

Программист видит **три метода**: `socket()`, `connect()`, `send()`. Никаких регистров, портов в Big-Endian, никаких `syscall` — всё спрятано.

### Уровень 2. Модуль `socket` в CPython

Интерпретатор Python — программа на C. Когда ты пишешь `s.send(b"Hello")`, вызывается функция `sock_send` из модуля `_socketmodule.c`, которая:

1. Проверяет типы аргументов.
2. Конвертирует Python-объекты в C-структуры.
3. Вызывает **системную функцию C** `send()` из glibc.
4. Получает результат, преобразует его обратно в Python-объект.
5. Если результат — ошибка, выбрасывает Python-исключение.

### Уровень 3. libc (glibc)

Функция `send()` из `libc.so.6` — это **обёртка над syscall'ом**. Внутри она:

1. Готовит аргументы в регистрах по соглашению Linux x86-64:
   - `RDI` = дескриптор сокета (число, пришедшее из Python).
   - `RSI` = указатель на буфер с данными.
   - `RDX` = длина буфера.
   - `RAX` = **41** (номер `sys_sendto`, потому что `send()` на уровне ядра — это `sendto` с нулевыми адресом и длиной).
2. Выполняет инструкцию **`syscall`**.
3. Проверяет `RAX`: если отрицательный — устанавливает `errno` и возвращает `-1`.
4. Возвращает результат в C-код Python.

### Уровень 4. Инструкция `syscall` в процессоре

Когда процессор встречает `syscall`:

1. Сохраняет **адрес возврата** в `RCX`, флаги — в `R11`.
2. Загружает **адрес обработчика** из MSR-регистра `IA32_LSTAR` (обычно это `entry_SYSCALL_64` в ядре).
3. Меняет уровень привилегий: **CPL 3 (Ring 3) → CPL 0 (Ring 0)**.
4. Переключает стек с пользовательского на **стек ядра** (через `TSS.RSP0`).
5. Передаёт управление функции `entry_SYSCALL_64`.

### Уровень 5. Ядро Linux

Функция `entry_SYSCALL_64` в `arch/x86/entry/entry_64.S`:

1. Сохраняет контекст пользовательского потока в `pt_regs`.
2. По номеру в `RAX` (= 41) находит нужный обработчик в **таблице `sys_call_table`**.
3. Вызывает `__x64_sys_sendto()`, которая:
   - Проверяет права доступа к дескриптору сокета.
   - Копирует данные из буфера пользователя в **TX-буфер ядра** (`sk_wmem_alloc`).
   - Планирует отправку пакета в сетевой стек.
   - Возвращает число отправленных байт или `-errno`.
4. Возвращается к `entry_SYSCALL_64`, который восстанавливает контекст.
5. Выполняет инструкцию **`sysretq`** — обратное переключение **Ring 0 → Ring 3**.

### Уровень 6. Сетевой стек

Дальше данные идут **без участия процесса**:

1. TCP-уровень строит сегмент: добавляет порты, sequence numbers, checksum.
2. IP-уровень строит пакет: добавляет IP-адреса, TTL, свой checksum.
3. Ethernet/Wi-Fi драйвер формирует кадр.
4. Сетевая карта **DMA**-передачей считывает данные из памяти и физически отправляет их в сеть.
5. Когда приходит подтверждение ACK, ядро помечает буфер как освобождённый.

### Уровень 7. NASM-клиент (наша программа)

В нашем ассемблерном клиенте **все промежуточные слои убраны**. Мы напрямую делаем то, что делает glibc:

```nasm
mov rax, 41         ; sys_socket
mov rdi, 2          ; AF_INET
mov rsi, 1          ; SOCK_STREAM
mov rdx, 0          ; protocol
syscall

mov r12, rax        ; сохранили дескриптор

mov rax, 42         ; sys_connect
mov rdi, r12        ; дескриптор
mov rsi, sock_addr  ; структура адреса
mov rdx, 16         ; длина структуры
syscall

mov rax, 1          ; sys_write (send = write для сокета)
mov rdi, r12        ; дескриптор
mov rsi, msg        ; данные
mov rdx, msg_len    ; длина
syscall

mov rax, 60         ; sys_exit
xor rdi, rdi
syscall
```

**Никаких libc, никаких Python-объектов, никаких исключений.** Только регистры и syscall'ы.

### Итоговая таблица трансформации

| Уровень | Что происходит | Кто отвечает |
|---------|----------------|--------------|
| 1. Python | `s.send(b"Hello")` | Программист |
| 2. CPython | `sock_send()` в C | Интерпретатор |
| 3. glibc | `send()` → `syscall(41)` | Системная библиотека |
| 4. Процессор | `syscall` → Ring 0 | Аппаратура CPU |
| 5. Ядро | `sys_sendto` в таблице syscall'ов | Linux kernel |
| 6. TCP/IP | Сегмент → пакет → кадр | Сетевой стек ядра |
| 7. NASM | `mov rax, 1` + `syscall` | Программист напрямую |

**Ключевой вывод:** метод `send()` в Python — это многослойная абстракция. Под капотом — обычный системный вызов `sys_write` с дескриптором сокета в `RDI`, указателем на данные в `RSI` и длиной в `RDX`. Ассемблер позволяет **убрать все слои** и работать напрямую с регистрами и ядром, что даёт максимальную производительность и полный контроль, но требует ручного управления памятью, байтовым порядком и проверкой ошибок.
