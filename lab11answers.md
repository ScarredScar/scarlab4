# Лабораторная работа №11. Ответы на контрольные вопросы

## Вопрос 1. Суть BlockingIOError (EWOULDBLOCK / EAGAIN)

`EWOULDBLOCK` (в Windows — `WSAEWOULDBLOCK`) и `EAGAIN` — это **два кода одной и той же ситуации**: «данных сейчас нет, но это не ошибка программы, попробуй позже».

### Что происходит на уровне ядра

Когда сокет находится в **блокирующем режиме**, вызов `recv()` или `accept()` работает так:

1. Процесс делает syscall `recv()`.
2. Ядро проверяет RX-буфер сокета: если **данных нет** — ядро **усыпляет поток** и помещает его в очередь ожидания данного сокета.
3. Планировщик переводит поток в состояние `S` (Sleeping), процессор освобождается для других задач.
4. Когда приходит пакет, ядро **будит** поток, и `recv()` возвращает данные.

**Поток ждёт — но не тратит CPU.**

### Что меняется в неблокирующем режиме

Когда сокет переведён в **неблокирующий режим** (`setblocking(False)`), ядро ведёт себя иначе:

1. Процесс делает syscall `recv()`.
2. Ядро проверяет RX-буфер: если **данных нет** — оно **не усыпляет** поток.
3. Вместо этого ядро **мгновенно возвращает управление** в Ring 3 и передаёт специальный код ошибки:
   - `EAGAIN` («попробуй ещё раз») или `EWOULDBLOCK` («эта операция заблокировала бы поток, но я не хочу») в Linux.
   - `WSAEWOULDBLOCK` (код 10035) в Windows.

### Почему ядро возвращает ошибку, а не ставит на паузу

**Это осознанное архитектурное решение.** В неблокирующем режиме программист сам хочет управлять ожиданием:

- Крутить цикл, попутно делая другую работу.
- Использовать мультиплексирование (`epoll`, `select`, `IOCP`), чтобы ядро само следило за множеством сокетов.
- Обрабатывать тысячи клиентов в одном потоке.

Если бы ядро в неблокирующем режиме **всё равно усыпляло** поток — смысл режима терялся бы. Поэтому ядро **честно сообщает**: «данных нет, я не стал тебя ждать, решай сам, что делать». Программа сама решает: подождать (`sleep`), продолжить цикл, переключиться на другой сокет.

`BlockingIOError` в Python — это исключение, через которое интерпретатор сообщает программе о полученном коде `EWOULDBLOCK` / `WSAEWOULDBLOCK`. Это **не сбой**, а **штатный сигнал** от ядра.

## Вопрос 2. Цена неблокирующего режима — 100% CPU без полезной работы

### Что происходит в цикле без `sleep`

Когда `time.sleep(0.01)` убран, цикл превращается в **непрерывный поток syscall'ов**:

```python
while True:
    try:
        client, addr = server.accept()
        break
    except BlockingIOError:
        pass   # ← пустая итерация
```

Каждая итерация — это **полный цикл перехода между уровнями привилегий**:

1. **Ring 3 → Ring 0.** Процессор выполняет инструкцию `syscall`: сохраняет контекст, загружает адрес обработчика из `IA32_LSTAR`, переключает стек на стек ядра, меняет CPL с 3 на 0.
2. **Ядро проверяет сокет.** Проверяет, есть ли новое соединение в очереди `accept`. Очередь пуста — нет данных.
3. **Ring 0 → Ring 3.** Ядро готовит возврат: устанавливает код ошибки `EAGAIN`, восстанавливает контекст пользовательского потока, выполняет инструкцию `sysret`, меняет CPL с 0 на 3.
4. **Python обрабатывает исключение.** Вместо возврата значения — выбрасывается `BlockingIOError`, интерпретатор ловит его, обрабатывает, переходит к следующей итерации.
5. **GOTO 1.** Цикл повторяется.

### Почему это сжигает 100% одного ядра

Процессор **никогда не простаивает** — он всё время выполняет **хоть и бесполезную, но реальную работу**: переходы между кольцами, проверки, обработку исключений. Ни одной паузы, где ядро могло бы заняться другими задачами.

**Накладные расходы на один оборот цикла:**

| Шаг | Примерная стоимость |
|-----|---------------------|
| Сохранение/восстановление контекста потока | ~100–200 тактов CPU |
| Переключение Ring 3 → Ring 0 | ~500–1000 тактов |
| Проверка очереди сокета в ядре | ~200–500 тактов |
| Обработка исключения в Python | ~1–3 микросекунды |
| **Итого** | **~2–5 микросекунд на итерацию** |

То есть **200 000 – 500 000 syscall'ов в секунду** — и всё это впустую, потому что данных нет. CPU полностью занят **посредничеством между пользовательским кодом и ядром**, а не полезной работой.

### Сравнение с блокирующим режимом

| | Блокирующий | Неблокирующий без sleep |
|---|---|---|
| Поток | Заснул, `S`, 0% CPU | Крутится, `R`, 100% CPU |
| Работа | Ждёт событие | Крутит пустые syscall'ы |
| Отзывчивость | Проснётся, когда нужно | Постоянно занят, но бесполезно |
| Полезность | Максимум для одиночного клиента | Только в связке с `epoll`/`select` |

Именно поэтому **неблокирующий режим без мультиплексирования** — это худший из вариантов: **и CPU сжигается, и ничего полезного не делается**. Это называется **busy-wait** или **polling** — активное ожидание.

## Вопрос 3. Как проблему решают промышленные серверы

Промышленные серверы (nginx, Node.js, базы данных, веб-фреймворки) **не используют чистый polling**, потому что он сжигает CPU. Вместо этого применяют **мультиплексирование ввода-вывода** — механизм, при котором **ядро само следит за множеством сокетов**, а поток засыпает до момента, когда **хотя бы один** из них станет готов.

### Основная идея

Вместо цикла:

```python
while True:
    for sock in all_sockets:
        try:
            data = sock.recv(1024)   # тратим время на каждый
        except BlockingIOError:
            pass
```

Программа делает **один** вызов ядру:

```python
ready_sockets = epoll_wait(...)   # ядро само проверяет все 10 000 сокетов
```

Ядро:
1. Ставит все переданные сокеты на **аппаратное наблюдение** (через очереди ожидания внутри структур `struct sock`).
2. Усыпляет поток.
3. Как только **хотя бы один** сокет получает данные (или закрывается, или готов на запись) — ядро **будит поток** и возвращает **массив дескрипторов**, готовых к работе.
4. Программа обрабатывает только **те сокеты, что действительно готовы**, а не все подряд.

### Реализации в разных ОС

**Linux: `epoll`**

- `epoll_create()` — создаёт объект epoll в ядре.
- `epoll_ctl()` — регистрирует сокеты в этом объекте.
- `epoll_wait()` — блокирующий вызов, ждёт событий на зарегистрированных сокетах.

Сложность: **O(1)** на событие, а не **O(N)** на весь список. Работает на 10 000+ сокетов в одном потоке без потерь CPU. Именно на нём работают **nginx**, **Redis**, **Node.js** (через `libuv`).

**Windows: `IOCP` (I/O Completion Ports)**

Работает **ещё глубже**: программа не ждёт готовности — она **сразу отдаёт ядру буфер** для чтения и говорит «заполни, когда данные придут». Ядро само читает из сети в этот буфер через пул потоков ядра и **уведомляет программу постфактум**: «данные лежат у тебя в буфере, забирай».

Сложность: ещё меньше накладных расходов, чем у `epoll`. Именно на IOCP работают **IIS**, **SQL Server**, высоконагруженные сервисы Windows.

### Сравнение всех трёх подходов

| Подход | Кто ждёт | CPU при простое | Масштабируемость |
|--------|----------|-----------------|------------------|
| **Блокирующий** (`accept`/`recv`) | Поток спит в ядре | 0% | 1 поток = 1 клиент |
| **Неблокирующий + polling** | Поток крутит цикл | 100% | Плохо масштабируется |
| **Мультиплексирование** (`epoll`/`IOCP`) | Ядро следит за всеми сокетами, поток спит | 0% при простое | 1 поток = 10 000+ клиентов |

### Что это даёт на практике

**Nginx** обслуживает десятки тысяч одновременных соединений на одном ядре CPU, потому что использует `epoll` (Linux) / `kqueue` (BSD) / `IOCP` (Windows). Поток **спит**, пока нет событий, и **мгновенно просыпается**, когда хотя бы один сокет готов. Никаких пустых циклов, никакого сжигания CPU.

**Node.js** — та же история: один поток + `libuv` (обёртка над `epoll`/`IOCP`/`kqueue`). Знаменитая асинхронность Node.js — это не магия, а именно **мультиплексирование** ввода-вывода.

**Вывод:** неблокирующие сокеты **сами по себе бесполезны** — они тратят CPU впустую. Смысл они обретают **только вместе с мультиплексированием**, когда ядро берёт на себя роль «наблюдателя» за всеми сокетами и будит поток только при реальных событиях. Это и есть архитектура всех быстрых серверов.
